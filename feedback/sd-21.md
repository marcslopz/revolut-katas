## A. Assessment: PASS (moderate)

**Time is fixed:** 45 minutes on the first try after sd-20's 62, with requirements at 8 minutes and every flow
walked aloud in the high level.

The cost of going faster showed up in what Phase 1 skipped. The rules that make this prompt interesting were
discovered late:
- waitlist when nothing is available
- holds that start when a copy is set aside
- a limit per user across libraries

Then the secondary transitions didn't fully carry them:
- new copies skip the waitlist
- the limit is never enforced
- `reservations` lost its library

## B. Three strongest things

1. **Time owned and met**: 8 / 10 / 26 minutes, with phase changes announced.
2. **Lessons transferred across mocks**: walking flows before the diagram (sd-20), the geo index for "near"
   (sd-18), Phase 4 opened unprompted, idempotency keys on the client and the notifications.
3. **Counters inside the same transaction as the status** on every path you designed (reserve, return, cancel,
   no-show, overdue).

## C. Three biggest risks for the real interview

1. **Fast requirements that miss the core rules.** Keep the 8 minutes, but spend 2 of them on *"what happens when
   X isn't available / when does each timer start / any limits per user?"*. For a reservation prompt those are
   the core requirements, not edge cases.
2. **Secondary transitions skip the shared structures.** Every event that frees a copy (return, cancel, no-show,
   **new copy**) must go through the same "serve the waitlist, else `available += 1`" function. Every event that
   adds or removes an active item must touch the user's limit counter.
3. **Timer races are still not unprompted.** "User at the counter as the expiry fires" needs a conditional
   `WHERE status = 'held'` on both sides, and you didn't state it.

## D. Architectural gaps or inconsistencies

- `reservations` without `library_id`, while the reserve call is `reserve(title, library)` and the waitlist is
  per library.
- `reserved_at` used for the 3-day timer, while the stated rule is "from when a copy is set aside" (a waitlisted
  user would expire immediately).
- New copies are added to `available` while users wait. That contradicts the FIFO rule you implemented for the
  other freeing events.

## E. Missing non-functional considerations

- DB HA (a hot standby) for 99.9%.
- A metric for the **waitlist length per title** (the hot-title signal), plus the age of the oldest hold.

## F. Over/under-engineering

- **Right-sized** throughout. **Under**: the per-user limit and the timer-race conditions.

## G. What a strong candidate might have covered

- **States as a table**:
  `waiting → held → picked_up → returned`
  `waiting/held → cancelled`
  `held → expired`
  `picked_up → overdue → returned`

  Each one is conditional on the previous state, and `held_at` starts the 3 days.
- **One `free_copy(library, isbn)` routine** that every freeing event calls. If someone is waiting, it promotes
  the first one to `held` and notifies them via the outbox. Otherwise it does `available += 1`.
- **Limit:** `users.active_items` with a conditional `+1 WHERE active_items < 5` on reserve and `−1` on
  return/cancel/expire, in the same transaction.
- **Shard by city/library**, so reservations, the waitlist and counters stay single-shard. The user's
  cross-library limit then becomes the cross-shard cost, which you'd name.

## H. Topics to practise before the next mock

1. **Phase 1 core-rule questions** for any reservation or stock prompt: unavailable → ?, when each timer starts,
   per-user limits.
2. **One freeing routine + one limit counter**, then walk every transition through both.
3. Keep the timing exactly as today.

## I. A better architecture (post-mock, brief)

Same boxes: an API, Postgres with a hot standby, a checker, and the notification service via an outbox.

**Data:**
- `library_books(library_id, isbn, copies, available)`
- `reservations(id, user_id, library_id, isbn, status, position, held_at, copy_id, picked_up_at, ...)`
- `users.active_items`

**Flows:**
- **reserve:** limit +1 (conditional), then either `available −= 1` → `held`, or append as `waiting` with a
  position.
- **free_copy:** either promote the head of the line to `held` (and notify), or `available += 1`.
- **checker:** expires `held` holds and marks `overdue` loans, both conditional, and claims rows with
  `SKIP LOCKED`.

## K. Real-world bonus (not scored)

- Real library systems (ILS such as Koha or Alma) call these **holds** with a **hold shelf** and **pickup
  expiry**, and often let a hold be filled by **any** branch's copy. That's the transfer you deliberately excluded.
- **Checkout limits** are usually per patron type (adult, child, student) and checked at the counter as well as
  at reservation.
- Popular titles get **"lucky day" copies**: some copies are excluded from holds and only lendable walk-in, to
  keep the waitlist from absorbing every copy.
