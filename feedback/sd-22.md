## A. Assessment: PASS (moderate, low margin)

**The core works** (scores 2 and 9 revised after the review, see below):
- two counters with a correct walk on every transition
- conditional updates in SKU order
- the checkout's order id as the hold's idempotency key
- a good late-payment rule

What lowers the margin:
- **The availability read**, the highest-volume path (5k/s, p99 < 100 ms), was never designed.
- **Scaling** went to sharding and a saga that the numbers don't require.
- *(Withdrawn after the review: edge cases were planned for the end of your DISE flow, and my probes came first.)*

## B. Three strongest things

1. **Two counters and a complete counter walk**, unprompted:
   - reserve: `available −`
   - success: `quantity −`
   - fail / expire: `available +`
   - add stock: both `+`

   This is exactly the sd-16 / sd-19 target ("counter walk on every transition, including secondary ones").
2. **Idempotent hold with the caller's id as PK**, plus `ON CONFLICT` → the same response. "Unique within what?"
   is answered right: there's a single caller.
3. **Late payment after expiry**: re-check availability, else refund. That's a business-aware recovery, not
   just "reject".

## C. Three biggest risks for the real interview

1. **The main read path is dropped.** In requirements you listed 5k/s reads with replicas, then never drew,
   designed or scaled them. In a stock or catalog prompt, *"how does the product page show availability at
   5k/s within 100 ms, and how stale may it be?"* is a first-class question. Answer it in the high level.
2. **Edge cases at the end can get pre-empted.** Your DISE flow puts them last, but an interviewer who
   probes first will think you missed them. Say it upfront in one line: *"I'll walk retries, crashes,
   concurrent writers and late events once the flows are done."* Then they wait, and the coverage counts as
   yours. Also lock the order row before the SKU rows when guarding a transition.
3. **Scaling by reflex instead of by numbers.** Start Phase 4 with *"200 holds/s is one writer; the first
   thing that breaks is X"*. Here X is the read path and hot SKUs, not write volume. Only shard when a
   number forces it, and pick the key that keeps the invariant row and its transaction on one shard.

## D. Architectural gaps or inconsistencies

- The diagram had the user calling `checkout` on the stock API, while the agreed boundary is the checkout
  service calling us.
- A `users` table with a type check and `orders.user_id` FK, but users authenticate elsewhere and the only
  write caller is the checkout service. Nobody populates it.
- "Users need credentials to check stock", right after "browsing is anonymous".
- `title` / `description` stored in `skus`, although the catalog was stated to be another service's.
- Requirements chose read replicas. The design never used them.

## E. Missing non-functional considerations

- **Callback authentication** for `payment_result` (mTLS or a signature from the checkout service).
- **Domain metrics:**
  - expired-hold rate
  - late-success-after-expiry and refund count
  - checker lag (age of the oldest overdue `reserved` order)
  - hold rejections per SKU (the hot-SKU and low-stock signal)
- **Read-path staleness SLA** (e.g. the product page may be ~1 s stale; the hold is always authoritative).

## F. Over/under-engineering

- **Over:** sharding by SKU + saga at ~200 holds/s.
- **Under:** the read path and its cache, hot-SKU contention, and the status guard on transitions.

## G. What a strong candidate might have covered

- **Phase 1:** *"Can we ever oversell?"* No, so the hold is the authoritative check, and the product page may
  be slightly stale.
- **Read path:** product page → cache (or replica) of `available` per SKU, with a short TTL or invalidation on
  change. 5k/s over 100k SKUs is trivial for a cache. The hold always goes to the primary.
- **State transitions as conditional updates** on the order row:

  ```sql
  UPDATE orders SET status = 'completed' WHERE id = ? AND status = 'reserved'
  ```

  The row count decides who won: success vs expiry. The loser does nothing, or follows the late path.
- **Checker:** `WHERE status = 'reserved' AND created_at < now() - 15 min … FOR UPDATE SKIP LOCKED`, with an
  index on `(status, created_at)`.
- **Hot SKU** (flash sale): contention on one row. Options:
  - keep it on one row; ~200/s of short transactions is fine
  - split stock into N sub-buckets per SKU
  - queue the holds for that SKU

  Name the cost of each.
- **Scaling progression:**
  - **local:** one writer + standby, plus the read cache
  - **regional:** a standby in another region, accepting the sync-replication latency against the 300 ms
    budget, or async with a small RPO
  - **global:** a cell per country, each owning its warehouse's stock

## H. Topics to practise before the next mock

1. **The read path for read-heavy NFRs**: when requirements give reads ≫ writes, design the read in the high
   level (cache / replica, staleness, which path is authoritative).
2. **Announce the edge-case sweep** at the start of the deep dive so it isn't pre-empted. Lock the order row first on every transition.
3. **Phase 4 from the numbers**: name the first bottleneck from the given rates before proposing sharding;
   choose a shard key that keeps the invariant transaction local.

## I. A better architecture (post-mock, brief)

Boxes: storefront → **read API + cache** (availability per SKU); checkout service → **stock API** (mTLS);
staff → stock API (JWT + staff role); stock API → **Postgres primary + standby**; **expiry checker** (SKIP
LOCKED).

Data:
- `skus(id, quantity, available, CHECK 0 <= available <= quantity)`
- `orders(id = checkout order id, status, created_at, …)` with an index on `(status, created_at)`
- `order_lines(order_id, sku_id, amount)`
- `payment_results(payment_result_id UNIQUE, order_id, outcome)`

Flows:
- **hold:**
  1. insert the order; on conflict, return the original response
  2. per line in `sku_id` order: `UPDATE skus SET available = available - n WHERE id = ? AND available >= n`
  3. if any line touches 0 rows, roll back
- **success / fail / expire:** a conditional update on `orders.status` from `reserved`, then the counters.
- **late success** (order already expired): re-hold if possible, else answer "refund" to the checkout service.

## K. Real-world bonus (not scored)

- Real shops often **reserve at "place order" rather than at cart**, exactly your rule. Some (e.g. ticketing,
  limited drops) also put a **virtual waiting room** in front of hot SKUs.
- Payment providers can confirm **after** a timeout: late webhooks and async 3-D Secure. That's why real
  systems keep a short **grace period** past the hold expiry, or re-reserve on late success as you proposed.
- Warehouse systems separate **on hand / allocated / available-to-promise (ATP)**. Your `quantity` /
  `available` is the minimal ATP model.
