## A. Assessment: PASS, strong

The **most proportionate design of all eleven mocks**: three boxes, one small Postgres, the right
data type for intervals, a DB-level non-overlap guarantee, and authZ in the WHERE clause. The two
HIGH items moved:

- **Data layer**: you said the lock while designing, and walking each query to its index made you
  catch missing columns yourself (`status`, `executed_at`). But the core field (`room_id`) was still
  missing at first. Better than sd-10, not closed.
- **Phase 4**: still needed a push, but after it you gave the model answer: numbers proving nothing
  breaks, contention per key, the real cost, and a consolidation with its schema consequence.

## B. Three strongest things

1. **Proportion**: no queues, no cache, no workers. The design matched ~3 QPS, and the 40x reasoning
   confirmed it still fits.
2. **Index walk per query**: create → delete → edit → book → cancel, each with its index or "PK
   already". This is the HIGH drill, done live.
3. **Phase 4 after the push**: numbers, contention per room, cost of 100 cells, consolidation to
   per-continent cells + `office_id`.

## C. Three biggest risks for the real interview

1. **The core field still goes missing on the first pass** (5th mock): `bookings` without `room_id`.
   Before presenting a table, read your main query against it.
2. **Phase 4 still starts with a push** (sd-8 to sd-11). You clearly know how to answer once asked.
   Open with "at 40x: N writes/s, M reads/s — nothing breaks; the cost is X".
3. **The main use case**: "find a free room" is what employees do most. Ask "what's the most common
   user action?" in Phase 1.

## D. Architectural gaps or inconsistencies

- Room-row lock (workflow) vs non-overlap table constraint (schema): two mechanisms for the same
  guarantee. Keep the constraint (it can't be bypassed by a code path that forgets the lock).
- `idempotency_key` moved from bookings/rooms to actions. Fine, but then the action insert must be in
  the same transaction as the change it protects (implied, not said).
- Slot-row storage estimate (pre-created rows per 15 minutes) vs the range-based `bookings` table that
  was actually designed.

## E. Missing non-functional considerations

- None significant for this scope. Optionally: time zones per office (store `tstzrange`, display in
  the office's zone).

## F. Over/under-engineering

- **Right-sized**: HLD, security, single Postgres.
- **Slightly over**: read replicas + routing at ~3 QPS; a cell per building (self-corrected).
- **Under**: the search-free-rooms query.

## G. What a strong candidate might have covered

- Phase 1: "the most common action is *find a free room for this time and size*" → design that query
  first.
- `bookings(booking_id, room_id, owner_id, slot tstzrange, status, title, created_at)` +
  `EXCLUDE USING gist (room_id WITH =, slot WITH &&) WHERE (status = 'reserved')`. One constraint gives
  correctness under concurrency **and** the index for overlap queries.
- Free rooms: `SELECT r.* FROM rooms r WHERE r.office_id = ? AND r.capacity >= ? AND r.status =
  'created' AND NOT EXISTS (SELECT 1 FROM bookings b WHERE b.room_id = r.room_id AND b.status =
  'reserved' AND b.slot && tstzrange(:from, :to))`. That's 200 rooms × a GiST probe, milliseconds.
- Phase 4 opener: "40x is 67 row writes/s and 111 QPS. Nothing breaks. I'd run one deployment per
  continent for latency, not one per building, because operating 100 cells is the real cost."

## H. Topics to practise before the next mock

1. **Phase 4 opener without being asked** (HIGH): one sentence of numbers + verdict + cost, every
   time.
2. **Read your main query against the table** before presenting it (HIGH): which column does the
   WHERE use?
3. **Ask for the most common user action** in Phase 1, and design that path first.

## I. A better architecture (post-mock, brief)

Same three boxes. Data layer: `rooms(+office_id, status)`, `bookings(+room_id)` with the GiST exclusion
constraint (no room lock needed), `actions(idempotency_key UNIQUE, executed_at)` written in the same
transaction. Free-room search with `NOT EXISTS` over the constraint's index. One deployment per
continent with a sync standby in a second region.

## J. Better options, decision by decision

| Your decision | Works? | Better option (if any) and why |
|---|---|---|
| Three-box HLD | ✅ Optimal | — |
| `tstzrange` for the slot | ✅ Optimal | — |
| Room-row lock → check → insert | ✅ Works | A **GiST exclusion constraint** makes overlap impossible at the DB level, even for a code path that forgets the lock, and needs no explicit lock |
| Index `(room_id, status, slot)` | ⚠️ | B-trees don't do range overlap; the exclusion constraint's GiST index on `(room_id, slot)` does |
| Idempotency via `actions` | ✅ | Insert the action in the same transaction as the change |
| AuthZ inside the cancel's conditional UPDATE | ✅ Optimal | — |
| Fail-fast validation (4 h, 30 days, hours) | ✅ Optimal | — |
| Read replicas + read-your-writes | ⚠️ Over | At ~3 QPS the primary serves everything; keep only a sync standby for availability |
| Per-day pagination for room availability | ✅ | Simpler than offset; drop `offset` from the API |
| Cell per building → per continent | ✅ After push | Start from the per-continent answer, with the numbers |

## K. Real-world bonus (not scored)

- **Calendar integration** (Google/Outlook): real room booking lives inside the calendar, and rooms
  are "resources" invited to events.
- **No-show release**: a room is auto-released if nobody checks in within 10–15 minutes (a door
  tablet or app check-in). It's the biggest real-world efficiency gain.
- **Recurring meetings**: the hard part in practice (expanding occurrences, conflicts on some
  occurrences, edits to "this and following").
- **Time zones**: offices in different zones; store instants (`tstzrange`), show office-local time.
